# regino-crypto

Encryption core for apps that protect sensitive personal data. Published so anyone can verify how the data is protected.

*Slovensky: šifrovacie jadro pre aplikácie s citlivými osobnými údajmi, zverejnené, aby si ktokoľvek mohol overiť, ako sú údaje chránené.*

| Part | What it does |
|---|---|
| `vault/` (Rust, `regino-vault`) | Encrypted local database – SQLite + **SQLCipher (AES-256)**, key in the OS keystore (Windows Credential Manager), `secure_delete` and `compact()` so deleted rows leave no remains inside the live database file and WAL, safe backup writes |
| `keys/` (Rust, `regino-keys`) | **Argon2id** (key from password), **backup code** (`backup_code`: the same 16-character code and Argon2id keys as the TypeScript side), **XChaCha20-Poly1305** (key wrapping and data sealing with authenticated context), **Shamir 2-of-3** (key splitting with integrity check), **recovery-code key** (HKDF-SHA256, identical to the TypeScript side), **device key** for quick unlock (Windows Hello / passkey PRF secret → HKDF-SHA256), **Ed25519 signatures** (`sign`: personal signing key, fingerprint, signed wrapped keys, signed member lists – identical to the TypeScript side), **group key code and id** (`group`) |
| `ts/` (TypeScript, `@regino/crypto`) | Recovery code – **12 Slovak words** by default (128 bits), optionally **24 words** (256 bits), with checksum, optionally from the **English word list** (standard BIP-39 list; the language only changes the words, not the secret, the QR code or the keys); **16-character backup code** `XXXX-XXXX-XXXX-XXXX` for quick backups of less confidential data (75 bits + check character, keys through **Argon2id**, `@noble/hashes`); **key from a password** (`passwordKey`, Argon2id byte for byte as Rust `kdf::derive` – since 0.16.0); **printable recovery sheet** with QR code (data only, no address, generated offline), **Shamir 2-of-3** key shares byte for byte compatible with the Rust side (`splitKey`, `combineShares`, a share as QR text `RGS1:…` / QR code – since 0.16.0, for apps without Rust), encrypted backups (**HKDF-SHA256 → AES-256-GCM**), PIN for switching users, **sync between devices** (records sealed with a group key, group key wrapped per device with ECDH P-256, pairing code, SAS with a commitment for pairing through a server), **device vault** (since 0.20.0: data key wrapped by a device key from the OS or a passkey PRF, a short PIN only as a gate – `docs/DEVICE-VAULT.md`), **inbox** (people without an account – e.g. a client filling in a form or signing a document in the browser – seal data to a practice's public key; the server carries it but cannot open it), **signatures** (`signing.ts`, Ed25519: a person's signing key, the sender's signature on a wrapped key, a signed member list that only an admin can continue – so a server cannot pass off its own key as a colleague's; `docs/SIGNING.md`) |

## How it fits together (example)

```
password ──Argon2id──► password key ──┐
recovery code (12/24 words) ──────────┼─ wraps ─► master key ─ wraps ─► client key ─ seals ─► client records
2 of 3 shares (paper / person / notary) ┘
```
- Deleting a client = discarding the client's wrapped key → its records become unreadable in the database and in every backup made **after** the deletion. A backup made earlier still contains the wrapped key, so after deleting a client the app writes a fresh backup and discards the older ones (`regino_vault::backups::discard_backups_before`), and tells the user that copies made elsewhere still contain the client (see `AUDIT.md`, question 16).
- Rows deleted from the local database: `secure_delete` is on (deleted content is zeroed inside the pages) and after deleting sensitive data the app calls `regino_vault::Vault::compact()` (WAL truncated, file rebuilt), so no remains of the rows stay inside the live database file or WAL. Out of scope: remains at the file-system level – truncation frees blocks without overwriting them, so old WAL frames and free pages can stay in the free space of the disk, on an SSD or in shadow copies; they are encrypted under the database key. Use full-disk encryption (BitLocker); see `AUDIT.md`, question 7 + 12.
- The core authenticates **what** a blob is and **where** it belongs (AEAD with a context), not **when**: a sealed record or wrapped key made a year ago still opens. Freshness, order, protection against replay or rollback (a server or storage returning an older genuine state) and tombstones for deletions are the app's job – prev-hash chain and version in the sealed payload, a rotation epoch, a per-device high-water mark; see `AUDIT.md` section 3.3 and the header of `ts/src/sync.ts`.
- Changing the password = re-wrapping the master key; data is not re-encrypted.
- No single share of the "2 of 3" opens anything on its own – not even the one held by the operator.

## Backup code or words?

| | 16-character backup code (since 0.15.0) | 12 / 24 words |
|---|---|---|
| Looks like | `R2FY-S7XG-EE8M-VGNX` | `abeceda batoh mreža …` (12 words) |
| Strength | 75 random bits + a check character; every guess costs an **Argon2id** (32 MiB, 2 passes – about 0.4 s in Node, 1–1.5 s on a phone) | 128 / 256 bits, no KDF needed |
| Offline attack on a stolen file | on average ≈ 6·10¹⁰ GPU-years (`AUDIT.md`, question 20); since backup version 4 (0.19.0) the same holds for stolen chunks and server ids – each user has their own salt | out of reach of any attacker |
| For | **less confidential data, quick backups** – e.g. a teacher's portfolio in Žiačik, later Gazda | **highly confidential data kept for years** – Dôverník (health data, art. 9 GDPR) stays on words |

Rules for apps that use the code:
- create it with `newBackupCode()` (or `newBackupCodeSecret()` + `formatBackupCode`), show it once with the printable sheet (`recoverySheetHtml(secret, …)` – a 10-byte secret gives the code sheet with a QR code `RGC1:…`), read it with `parseBackupCode(input)` (lower case, spaces, hyphens and `O/I/L` are fine; errors say which character or that the check failed);
- `encryptBackup(codeSecret, payload, createdAt, app, chunks?, { kdf?, params? })` writes a **version-4** backup (since 0.19.0) with the random salt and the Argon2id parameters in its header; `decryptBackup` and `openBackup` read versions 1–4;
- **chunks with a code (version 4):** the chunk keys come from the salt and parameters of the backup – `params = newBackupCodeParams()` for the first backup, `backupCodeParamsOf(previousBackup)` for the next ones (so unchanged chunks keep their names), then `backupChunkKeys(codeSecret, app, params)` and `encryptBackup(…, chunks, { params })`; when restoring, `backupChunkKeys(codeSecret, app, backupCodeParamsOf(file))`. Without `params`, `backupChunkKeys` gives the keys of version-3 backups (to read them);
- if a server has to recognise backups by the code, store `backupIdForServer(secret, app, params)` (version 4: it needs the salt from the backup header) and **limit the attempts** of anyone asking by id, as for a login. The version-3 id `backupCodeId` (fixed salt of the application) was removed in 0.21.0.

## How to verify that an app really uses this core

1. **Open your backup independently:** download [`tools/open-backup.html`](tools/open-backup.html) (a single file that runs offline in the browser), select a backup from the app and enter your 12 or 24 words – Slovak or English, the list is recognised from the words – or your 16-character backup code (or a photo of the QR code from the recovery sheet). If it opens, the app encrypts with this public code. The file is built from the sources in `ts/` and an automated check ensures it does not differ from them.
2. **Version in the app:** the "About" screen shows the core version and commit, e.g. "regino-crypto 0.3.0 (1a2b3c4)" – compare it with the [releases](https://github.com/TPCreator/regino-crypto/releases).
3. **Software bill of materials (SBOM):** every release of the core and of the app comes with a machine-readable list of all libraries (CycloneDX) and SHA-256 checksums.

## Rules
- Only well-reviewed libraries (RustCrypto, dalek, SQLCipher, WebCrypto, noble) – no home-grown cryptography.
- Format version in the header of every wrapped key and backup.
- Tests on every change (`cargo test --workspace`, `npx vitest run --coverage` in `ts/` with 100 % coverage enforced for the TypeScript part; Rust coverage with `cargo llvm-cov`, at least 95 % of lines, and fuzzing of the Rust parsers since 0.16.0).
- Independent security audit before production use.
- **Apps that use the Rust crates** (`regino-vault`, `regino-keys` as a git dependency) keep the **same versions of the Rust dependencies as `Cargo.lock` of the core** at the pinned commit – only that combination is tested here. The app checks it in its CI (e.g. compares the versions of the shared packages in its own `Cargo.lock` with the core's) and moves them together with the core, never alone.
